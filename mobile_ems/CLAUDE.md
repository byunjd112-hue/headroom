# IFPS 이동형 전력체계 EMS — 작업 규칙

## 리비전 관리 (사용자 요구, 반드시 지킬 것)

- 실행 패키지, Word 문서, 장치별 안내서, 보고자료 PPT, 하드웨어 구성 기술자료 PPT, 제안 발표 자료 EMS 보완본, FMEA·FTA 워크벤치(HTML)는 **모두 같은 리비전 번호**를 쓴다. 번호는 `VERSION` 파일 하나에만 적는다(예: `Rev18`).
- 소스·설정·문서 내용 중 어느 하나라도 바꿔 사용자에게 전달할 때는:
  1. `VERSION` 을 다음 번호로 올린다.
  2. `python docs/build_all.py --measure` 로 측정과 **전체 문서**를 다시 만든다(일부 문서만 다른 번호로 만들지 않는다).
  3. 커밋한 뒤 `python docs/build_all.py --zip` 으로 `IFPS_Mobile_EMS_<Rev>.zip` 과 문서 묶음 `IFPS_EMS_문서_<Rev>.zip` 을 만든다. 문서 묶음을 리눅스 `zip` 명령으로 만들지 않는다(한글 파일 이름이 Windows 에서 깨진다).
- `docs/out` 에는 현재 리비전 산출물만 둔다. 이전 리비전은 `build_all.py` 가 지운다(이력은 git).
- 문서는 Word(.docx)와 PowerPoint(.pptx)로 전달한다. PDF 는 만들지 않는다(사용자 요청).
- 화면(HMI) 아래쪽과 디버그 → 시스템 정보에 패키지 리비전이 표시된다. 전달 전 확인한다.

## 그 밖

- 사용자에게는 한국어로, 쉬운 말로 설명한다. "무소음" 대신 "저소음"을 쓴다.
- 참고 PPT 의 이미지는 잘라 쓰지 않는다(참조해서 새로 만든다).
- 운용 장소 용어는 "작전지"와 "주둔지"를 쓴다("전개지"라고 쓰지 않는다). 보고자료는 운용 방안을 한 장(章)에 모아 작전지 운영 → 주둔지 운영 순으로 설명한다.
- 화면이 바뀐 리비전에서는 `docs/ppt/capture.js` 로 화면을 다시 찍어 보고자료에 넣는다. 캡처는 모의 시각 13시(낮)로 찍는다 — 밤에 찍으면 태양광이 0 이라 꺼진 것처럼 보인다(주둔지에서도 이동형 태양광을 쓴다).
- 보고자료 PPT 디자인은 `docs/ppt/build_deck.js` 의 참고 발표 자료 양식(갈색 머리띠·크림색 카드)을 유지한다.
- 제안 발표 자료 EMS 보완본은 사용자 원본(`docs/ppt/base/`, 저장소 제외)에 EMS 4장을 넣어 만든다. 용량 25 MB 이하(스크립트가 확인), 결과물도 저장소에 올리지 않고 문서 묶음 zip 에만 넣는다.
- FMEA·FTA 워크벤치는 `docs/fmea/`(자료 `data_fmea.py`·`data_fta.py`)에서 만든다. 소프트웨어 기능이 바뀌면 '현 예방대책'과 근거 추적표(S09)를 함께 고치고, 화면의 무결성 점검이 전부 정상인지 확인한다. S·O·D 는 제안값이라고 밝힌다.
- 설정 편집기(`ifps_ems_rt/hmi/cfgedit.py`, 화면 `static/cfgedit.js`)는 설정 파일 두 개(runtime.json·pointmap.csv)만 고친다. 파이썬 소스 편집 기능은 넣지 않는다(형상 통제). 새 설정 항목을 만들면 `check_runtime` 의 범위 검사에도 넣는다.
- **C++ 이식은 Rev27 상태에서 멈췄다(사용자 결정). 앞으로는 파이썬 판만 갱신하고, 사용자가 요청할 때만 C++ 로 옮긴다.** 단, `ifps_ems_rt/opsmode.py`·`modbus.py`·`pointmap.py` 의 계산을 바꾸면 `python tools/cpp_report.py` 의 동등성 시험이 깨지므로, 그때는 사용자에게 알리고 C++ 쪽을 맞출지 묻는다.
- C++ 핵심부(`cpp/`, 1·2단계(가)까지 이식)는 MISRA C++:2008 기준이다: C++03 문법, 동적 메모리·예외·매크로·공용체·재귀 없음, 함수당 return 하나, static_cast 만, 크기가 드러나는 자료형(u8·u16·u32·i32·f64). 파이썬 판이 기준 구현이며 논리를 고치면 양쪽을 함께 고치고 `python tools/cpp_report.py` 로 동등성·실행률·정적 점검을 다시 본다(정적 경고 0, 기계 점검 위반 0 유지). 공인 도구 결과가 아니라고 문서에 밝힌다.
- 시연(가상 장치) 모드의 예측은 `results/demo_live.csv`(합성 자료를 지금 시각까지 잇고 가상 장치 실측을 덮어쓴 것)로 계산하며 15분 구간마다 다시 계산한다. 실장치 모드는 실측 이력 8일이 쌓여야 예측한다.
- 지속 학습(`ifps_ems/learner.py`): 주기적 재학습 → 학습에 쓰지 않은 구간으로 검증 → 통과한 종류(부하·태양광 각각)만 적용. 학습은 별도 프로세스로 돌린다(제어 주기 보호). 검증 없이 모델을 바꾸는 경로를 만들지 않는다. 설정은 runtime.json 의 `ai`.
- 운용 장소 × 태세 9가지의 정의는 `tests/test_ops.py` 의 `test_mode_matrix_…` 가 기준이다. **주둔지 자립 태세 = 전시·유사시 상전 상실(사용자 정의)**: 수전 차단기가 열려 있으면 정전 논리(ESS·태양광·주둔지 발전기)로 운전하고, 가상 장치에서는 자립을 고르면 차단기를 연 상태로 모사한다. 태세가 자립인데 차단기가 투입 상태면 경보를 내고 수전을 최소로 묶는다(EMS 는 수전 차단기를 조작하지 않는다; `garrison_step(self_supply=True)` — C++ 판에 없음). 디젤 연료는 50% 이하 또는 8시간분 이하에서 보충 경보를 내고 보충까지 다시 알린다(runtime.json 의 `fuel`).
- 시험: `python -m unittest discover -s tests`. 신뢰성 기준(복잡도 20, 인자 8, 중첩 5, 함수 200줄)은 `python tools/static_report.py` 로 확인한다.
- 태양광 예측 보강(Rev30): 하늘 카메라 구름량(`ifps_ems/skycam.py`, 연결 `hmi/skywatch.py`, 설정 `skycam`, 이력의 `sky` 열)과 주의집중 예측(`ifps_ems/attn.py`)을 릿지 회귀에 구간별 비율 α 로 섞는다(`forecast.py`). α 는 검증에서 2% 이상 좋아질 때만 0 보다 크다. 예측 시점 뒤의 자료를 쓰지 않는다(시험 있음). 효과 수치는 `docs/ppt/pv_ai_eval.py` 로 다시 재서 그대로 싣는다(합성 자료 결과이고 카메라가 15~30분 앞 구름을 본다는 가정이 있음을 밝힌다 — 과장 금지).
- 시험은 개발 폴더의 `results/` 모델을 바꾸지 않게 임시 폴더 복사본을 쓴다.
- AI 예측 기술자료 PPT(`docs/ppt/build_ai_deck.js`)와 논문 Word(`docs/build_ai_paper.js`)도 같은 리비전으로 함께 만든다. 수치는 `docs/ppt/ai_paper_eval.py` → `ai_paper_eval.json` 에서만 읽는다. **모델 그림은 수식과 연결된 실제 값으로 그린다(사용자 요구)**: `node docs/ppt/ai_render3d.js <three 경로>` 가 학습된 가중치·거리·중요도·비율을 3차원에 그대로 놓고 렌더링하며 그림마다 수식 기호를 적는다. 비유용 AI 생성 이미지를 모델 그림으로 쓰지 않는다(설치 예시 사진만 '개념도'라고 밝혀 쓴다). 예측 코드나 합성 자료를 바꾸면 평가 → 입체 그림 → `ai_charts.js` 순으로 다시 만들고, 논문 5·6장의 서술(어느 구간에서 좋아지고 그대로인지)이 새 수치와 맞는지 읽어 확인한다. 참고문헌은 실제로 있는 문헌만 싣는다.
- **Rev32 는 사용자가 보완해 올린 판이다(단기 실측 앙상블 `ifps_ems/nowcast.py`, 운영 시나리오 검증기 `hmi/scenarios.py`·`scenario_policy.py`·`static/scenarios.js`, 원시 관측 표시, 계획 재계산 보강). Rev33 부터 이 소스를 기준으로 한다.** 그 코드의 문체(영문 독스트링, 줄 나눔)는 그대로 둔다.
- 예측 구간은 `forecast.py` 의 `calibrate` 가 변동 여유(최근 2일 포함률이 75% 아래면 80%를 덮도록 배율 s 를 곱함)를 넣어 맞춘다. 독립 시험은 `python -m tools.forecast_benchmark --out docs/forecast_benchmark.json`(운용처럼 매일 보정, 시드 6개). `docs/forecast_benchmark_static.json` 은 Rev32 상태(학습 때 한 번 보정, 변동 여유 없음)의 비교 기준이므로 다시 만들지 않는다. 예측 코드를 바꾸면 벤치마크 → `ai_paper_eval.py` → `ai_render3d.js` → `ai_charts.js` 순으로 다시 만든다(약 10분).
- 시나리오 결과는 `python -m tools.scenario_report`(build_all --measure 가 부른다). 한 건(디젤 기동 응답 지연)은 일부러 실패시키는 시험이다 — 결함으로 적지 않는다. 제안된 대기 시간은 현장 보호 설정값이 아니라고 문서에 밝힌다.
- 문서 묶음 zip 은 읽는 순서 폴더(01_제안발표 ~ 07_시험과신뢰성, 08_시험근거)와 `00_…문서안내.html` 로 만든다(`build_all.py` 의 `LAYOUT`·`EVIDENCE`). 새 문서를 만들면 `LAYOUT` 에 넣는다(안 넣으면 묶을 때 오류). 문서 내용은 덧붙이지 말고 해당 절에 넣는다(사용자 요구: 양식·순서 정리) — 문서 안에 이전 리비전 번호가 남지 않게 한다.
- FMEA Excel 내보내기는 군 MG FMEA·FTA 통합분석서(Rev06)와 같은 시트 구성·순서(00_표지 ~ 18_약어·참고문헌, 19_변경이력)로 EMS 내용을 만든다(`docs/fmea/app.js` 의 `exportXlsx`). 사용자의 MG 원본 파일을 문서에 넣지 않는다.
- 운영 시나리오 화면의 시퀀스 다이어그램(`static/scenarios.js` 의 `sequence`·`route`)은 UML 식으로 그린다(사용자 요구): 머리에 장비 사진(`static/photos/<이름>.jpg`, 없으면 장비 코드), 세로 생명선과 활성 막대, 지령·입력은 실선, 응답 판정은 점선, 고장 주입은 주황 점선. 검증 결과(✓·✕, 관측값, 경과 시간, 실패 사유)를 선 위에 직접 보인다. 편집은 끌어서 순서 이동·삽입, 복제, 키보드(↑↓, Alt+↑↓, Delete).
- 운영 시나리오의 구성도 보기(`static/scentopo.js`, 사용자 요구 1단계): 장비 사진 블록·배전반(모선 A·B)·차단기 12개를 입체 블록으로 놓고 단계마다 신호·전력 흐름을 재생한다. 모선 구성은 결선도(`sld.js`)와 같게 유지한다. 상태 값은 검증기가 단계마다 남기는 `snap`(scenarios.py 의 `SNAP_PREFIX`·`SNAP_SUFFIX`)이다. 블록을 누르면 그 블록의 신호로 단계를 넣고, 끌면 배치가 브라우저에 저장된다. **2단계(미구현)**: 목록에 없는 새 장비·차단기를 추가하는 기능 — 대응표 등록과 가상 장치 동작 모형이 함께 필요하다. 보호 협조(계전기 정정·동작 곡선)는 모형에 없다.
- 시나리오용 추가 설비(2단계, `hmi/scenextra.py`, 정의 `config/scenario_extra.json`, 화면의 '설비 구성'): 급전선(차단기·고장 코드·kW), 변압기(부하율), 보호 계전기(정한시 과전류 — 감시 전력이 정정값을 정한 시간 넘으면 트립)를 **가상 장치에만** 넣는다. 실제 대응표·운전 설정은 바꾸지 않는다(시험으로 확인). 기본 정정값은 기존 기본 시나리오의 부하 크기(최대 100 kW 안팎)에서 오동작하지 않게 잡은 가정값이다 — 바꾸면 `python -m tools.scenario_report` 로 전체 시나리오를 다시 본다. 미구현: 반한시 곡선, 지락·부족전압 요소, 차단 실패 후비, 실장비 모드 표시.
- Rev37 에서 2단계의 남은 항목을 넣었다: 계전기 요소(과전류 oc·지락 gf·부족전압 uv), 시간 특성(정한시 dt·IEC 반한시 si/vi/ei), 차단 실패 후비(`backup`·`bf_ms`, 모사 신호 `STK.<차단기>`), 지락 전류 입력 `GF.<급전선>`, 급전선의 `ems`(EMS 가 보는 `LOAD.kw` 에 반영)·`photo`, 그리고 '실시간' 보기(지금 장치 값으로 구성도 — 실장비 모드에서도 열리며 표시 전용, 값이 없으면 '값 없음'). 부족전압은 정상 전압을 한 번 본 뒤에만 동작한다. 기본 시나리오는 27건(`MAX_CASES` 32). 여전히 없는 것: 방향성 요소, 재폐로, 계전기 간 통신(연동 차단), 추가 부하의 등급별 자동 차단 반영.

## 기록 보관소 · 보고서 (Rev38~)
- 보관소는 `ifps_ems_rt/archive.py`(SQLite, 표준 라이브러리). 화면부 연결은 `hmi/archwatch.py`, 조회 API 는 `hmi/archapi.py`, 보고서는 `hmi/report.py` + `hmi/docx.py`(표준 라이브러리 Word 작성기). server.py 는 줄 수 한도에 가까우니(engine.py 는 Rev54 에서 기능별로 나눔) 새 기능은 이 모듈들에 넣는다.
- 기본값: 저장 주기 15분, 보관 4년(1~5년), 512 MB. 보관 4년의 근거는 전기안전관리법 시행규칙의 점검 기록 보존 기간. 저장 주기를 정한 법령 조항은 확인하지 못했다 — 문서에 "법정 주기"라고 쓰지 않는다.
- 가상 장치 모드의 시연용 과거 자료(src=1)와 시연 점검 기록은 화면·보고서에 합성이라고 표시한다. 누적 지침은 EMS 적산값이며 정산용 계량기와 다를 수 있다고 적는다.
- 기록 조회기(`ifps_ems_rt/archview.py`, viewer.bat/sh)는 읽기 전용, 127.0.0.1 전용. `static/archive.js` 는 EMS 화면과 조회기가 같이 쓰므로 core.js 의 함수에 기대지 않게 쓴다(있으면 쓰고 없으면 넘어가게).
- 보고서 파일 이름은 영문·숫자만 쓴다(한글 이름은 브라우저에 따라 깨진다).
- ESS 안전 운영정보(`ifps_ems_rt/archdev.py`, 1분)와 장치별 자료, 주둔지 서버 전달(`archxfer.py`, 수신기 `archrecv.py`)도 같은 보관소에 든다. 항목 파일 `config/ess_safety.csv` 는 초안이다 — 전기안전공사의 정식 75개 항목 명세는 확보하지 못했으니 "공사 규격 준수"라고 쓰지 않는다. 미수집 항목은 0 + 미수집 표시.
- 전달 이력(표 xfer)은 보관 기간 정리로 지우지 않는다. 전송 주소는 설정의 archive.server_url 만 쓴다(요청으로 받지 않는다).

## 시퀀스 문서 · 수집 항목 · 조치 안내 · 설명서 · 교육 자료 (Rev39~)
- 시퀀스 PPT 는 `hmi/pptx.py`(표준 라이브러리 작성·읽기)와 `hmi/seqppt.py`. 다시 올릴 때는 '시나리오: …' 글상자와 '번호·종류…' 표만 읽는다. 표의 열을 바꾸면 내보내기·읽기·설명서의 표를 같이 고친다.
- 수집 항목 관리는 `hmi/archcfg.py` — 저장하면 runtime.json 의 archive 와 ess_safety.csv 를 쓰고 `ArchWatch.reconfigure` 로 바로 적용한다.
- 조치 안내(`static/troubleshoot.json`)는 경보 키의 앞머리(match)로 찾는다. 새 경보를 만들면 여기에 항목을 넣는다. 부품은 종류만 적고 품번을 지어내지 않는다.
- 사용자 설명서 본문은 `static/manual.json` 하나다(화면 도움말과 Word 가 같이 쓴다). 화면·기능을 바꾸면 이 파일의 해당 절을 고친다. 그림은 빌드 때 `static/manual/` 로 복사된다.
- 교육 자료는 실제 화면과 같아야 한다(사용자 요구). 교육 창은 `static/train.js`(가상 장치 모드 전용), 설치 없는 묶음은 `tools/build_training.py` 가 실제 static 을 복사하고 녹화한 응답을 넣어 만든다 — 따로 그린 화면을 만들지 않는다. 묶음의 값은 녹화한 장면이라 "계산한다"고 쓰지 않는다. 화면의 API 를 바꾸면 `train_mock.js` 와 녹화 목록(SCENE_GET·GLOBAL_GET)을 같이 본다.
- 교육 자료는 PC 와 휴대전화·태블릿 모두에서 돼야 한다(사용자 요구, Rev40). 작은 화면 처리는 `train.js` 의 small()/fit() 과 style.css 의 `html.tr-m` 규칙. 파일 하나짜리(`_모바일.html`)는 그림을 TRAIN_ASSETS 로 넣고 train_mock.js 가 경로를 바꿔 끼운다 — 새 그림 폴더를 쓰면 single_file 의 목록에 넣는다. index.html 의 viewport 에 minimum-scale=1 을 지우지 않는다(지우면 휴대전화가 화면을 줄여 버려 작은 화면 판정이 깨진다).
- 교육 창은 화면·탭·누른 항목에 맞게 내용이 바뀌어야 한다(사용자 요구, Rev41). 화면을 새로 만들면 `train.js` 의 PAGE(화면 설명·단원 번호), 탭이 있으면 SUB, 새 종류의 항목이면 TIPS 에 넣는다. PC 에서는 교육 창을 화면판 옆에 나란히 둔다(가리면 과제의 단추를 못 누른다).
- 시나리오 기본안은 정상 운전뿐 아니라 고장 대응(FMEA)·보호 협조(FAT)를 함께 둔다(사용자 요구, Rev42). 새 기본안에는 `cat`·`ref`·`fat` 을 넣고, `fat` 은 FMEA 의 verify 글을 쓴다(지어내지 않는다). 운전 모드 12건은 파일의 맨 앞에 둔다(scenario_report 의 N_MODE). 화면 목록은 [시나리오 고르기] 창 하나로 한다(꼬리표 줄을 되살리지 않는다).
- 시나리오는 FMEA·FAT 와 이어져 있어야 한다(사용자 요구, Rev43). 고장 대응 기본안의 `ref` 는 FMEA 번호, FMEA 워크벤치의 '시나리오·FAT 연결'(vScn)은 docs/scenario_results.json 을 읽는다 — 기본안을 바꾸면 `python -m tools.scenario_report` 뒤에 FMEA 를 다시 만든다(build_all --measure 가 이 순서로 한다). 별도 FAT 절차서가 없으므로 FAT 항목 번호를 지어내지 않는다.
- 환망은 `hmi/scenring.py`(가상 장치 전용 모형). 구간 차단·절체 시간은 가정값이라고 적는다. 실제 구간 차단·절체는 보호·배전 자동화가 하고 EMS 는 감시한다고 쓴다.
- 환망(Rev44~): FSU = 구간분전함(배치도의 FSU 와 같은 것), PPDU = 20 kW급 초경량 휴대용 배전체계 PPDU-20(사용자가 준 상세기술자료 HAES-IFPS-PPDU-TD-001 기준: 주 차단기 40 A, 6회로, CH2 환상 연결용, 접지저항 100 Ω 인터록, 5초 이내 우회). 전력 흐름은 ⑥ 배전체계 → FSU → PPDU → 6회로 → 시설 부하. 중요 부하 = 1등급 회로가 물린 PPDU. PPDU 끼리의 환상 연결·무선 통신은 아직 넣지 않았다(문서에 그렇게 적는다). 신호는 실제 대응표에 있다(가상 신호는 단선 입력 BRK.<n> 과 RING.ok 뿐). 계산 `ifps_ems_rt/ring.py`, 화면부 `hmi/ringwatch.py`·`static/ring.js`. 배전체계 구성은 운용자, 가상 조작은 엔지니어(ID 확정은 자동 인식을 끈 고정 배치에서만 쓴다). 조회 경로는 `/api/archive/ring`(서버 처리기 줄 수 한도 때문에 archive 갈래에 붙였다).
- 장치 자동 인식(Rev44~, 사용자 요구): 작전지마다 장치 자리·대수·종류가 달라지므로 화면 조작 없이 EMS 가 ID 를 읽어 화면을 스스로 구성해야 한다. 환망은 `ring.layout`(자리마다 읽은 ID = 그 자리의 장치, 구성은 ID 를 따라감, ID 0 = 빈 자리), 주 장치는 `ifps_ems_rt/fleet.py`(같은 종류 여러 대: 추가 자리 DG2 … 를 devices 에 두면 응답하는 것만 세어 합산·지령 분배, Rev45~)와 `hmi/autodev.py`(켠 뒤 한 번도 응답 없으면 미설치). 종류 이름의 값(DG.kw 등)은 합산값이므로 장치 하나의 값이 필요하면 `rt.fleet.unit()` 을 쓴다. 화면은 `KF/kN/kOn/kAbsent/kLost`(app.js)로 종류 단위 상태를 본다 — `D.DG.on` 처럼 첫 장치만 보지 않는다. '초기 기동 점검'은 인식 결과를 보여 주는 창일 뿐이다. 새 장치 기능을 넣을 때도 '사람이 배치를 입력해야 동작'하게 만들지 않는다.
- 날씨 입력(Rev46~, 사용자 요구): 장병의 수기 입력(작전지)과 군 통신망 수신(주둔지)을 태양광 예측에 섞고 AI 예측과 견주어 반영 비율을 정한다. 계산 `ifps_ems_rt/weather.py`, 화면부 `hmi/weatherwatch.py`, 화면 `static/weather.js`. 수기 입력은 장병이 휴대폰 날씨 앱(구글 날씨 등)에서 볼 수 있는 항목(날씨 표기 · 강수 확률 · 기온 · 기간)만 묻는다 — 운량·일사량 같은 전문 값을 입력란에 넣지 않는다(사용자 요구). 통신망 자료 형식과 날씨→운량 환산표는 가정이라고 적는다. 효과 수치는 `python docs/ppt/wx_eval.py` → `docs/ppt/wx_eval.json` 에서만 읽어 싣는다(AI 기술자료 · 논문 4.8 · 5.5 · 보고자료 · 설명서 · README). weather.py 의 계산이나 가정(앱 · 통신망 예보 오차)을 바꾸면 다시 돌리고, 나빠지는 구간(1시간 이내)도 그대로 적는다. 받는 주소는 설정의 weather.url 만 쓴다. engine.py 는 줄 수 한도(1000)에 닿아 있으니 새 기능은 별도 모듈에 넣고 엔진에는 줄을 늘리지 않는다.
- 통합 점검은 `python -m tools.soak_check`(가상 장치, 약 5분). 감시·제어·자동 인식을 건드린 리비전에서는 한 번 돌려 본다. 빌드에는 넣지 않았다.
- 환망 연동(Rev46~, 사용자 요구): 환망 화면의 단선 · 차단 구간 · 장치 이름은 개요 · 결선도 · 설비 제어 · 시나리오 · 기록 보고서에 같은 이름으로 나와야 한다. 화면들은 snapshot 의 `ring` 과 `RingView.fromSnap/sum/ends`(ring.js)를 같이 쓴다. 결선도는 환망을 별도 띠나 부하 아래가 아니라 모선과 부하 사이에 그린다 — 모선 A → 환망 → 배전체계 → 등급별 회로 → 부하(`sldRing`, 사용자 요구). 부하선은 케이블 구간 중간이 아니라 구간분전함(마디) 아래의 배전체계에서 내린다 — 구간에서 내리면 그 구간이 끊길 때 부하가 끊기는 그림이 된다. 부하 그림은 구간분전함 바로 아래에 실선으로 단다(구간분전함 → 배전체계 → 등급별 회로 → 그 시설 부하) — 한 구간이 끊겨도 반대쪽에서 받아 부하가 살아 있는 것이 보여야 한다(사용자 요구). 등급별 합계와 CB-L1~3 은 맨 아래 한 줄 글로 둔다. 환망의 구조는 양쪽 급전이다(Rev47 확정): 모선 A → 급전 A(구간 0) → 구간분전함 1 → … → n → 급전 B(구간 n) → 모선 B. 첫 · 마지막 구간분전함은 배전 · 변압의 모선을 거쳐 이어진다. 계산은 `ring._fed`. 개요 배치도는 구간분전함 그림을 놓인 자리 순서로 환망에 맞추고(`fsuRing`), 발전 장비는 배전 · 변압(모선)으로, 부하 시설은 구간분전함으로 잇는다 — 구간분전함은 부하 쪽 간선이다(PPDU 자료의 계층). 발전 장비 사이에 구간분전함을 두는 구성은 근거 자료가 없어 넣지 않았다 — 화면마다 따로 계산하지 않는다. 상시 개방점은 PPDU-20 자료의 "NOP 1개소 반드시 유지 — 순환 전류 방지"가 근거다(닫힌 고리 운용은 넣지 않는다).
- EMS 전원(Rev47~): 하드웨어 설계는 입력 3종(상전 · 배전 모선 · 차량 28 V) 자동 절체 + 온라인 무정전 전원이다. 화면 · 문서에서 EMS 전원을 모선 한 줄로만 그리지 않는다(사용자 지적). 무정전 전원의 상태 신호는 아직 대응표에 없어 `ems.power` 경보는 모선 전압으로 추정한다 — 그렇게 적는다. 구간분전함의 통신선도 배치도에 그린다.
- 환망 가상 연습(Rev47~): 단선을 풀면 복구 절차(구간 재투입 → 상시 개방점 다시 개방)로 넘어가야 한다(`ring.Model._repair`). 풀어도 차단이 남아 다음 연습이 엉키면 안 된다(사용자 지적).
- 환망 구조(Rev47 확정, 사용자 결정): 결선도는 '모선 A ─ 환망 급전 A ─ 구간분전함 1 … n ─ 환망 급전 B ─ 모선 B' 양쪽 급전 그림을 유지한다. 복귀선(FSU n → FSU 1) 한 줄 구조로 바꾸지 않는다.
- 화면 연동(Rev47~, 사용자 요구): 모든 화면은 같은 상태를 보여야 한다. 화면이나 환망 · 자동 인식을 건드리면 가상 장치를 띄우고 `node tools/link_check.js` 로 대조한다(약 6분, 어긋남 0 이어야 한다). 시나리오 화면의 장비 그림은 `photos/` 에 있는 것만 쓴다(없는 이름으로 <img> 를 내면 깨진 그림이 보인다 — 수전해는 fc 그림).
- 운영 시나리오의 '구성도' · '실시간' 보기에는 환망 그림을 넣지 않는다(사용자 요청, Rev48). 보고자료의 환망 그림(scen_ring)은 환망 화면에서 찍는다. 환망은 환망 · 개요 · 결선도 화면에서 본다. 개요 배치도에는 첫 · 마지막 구간분전함이 배전 · 변압 안의 모선으로 이어진다는 표기를 둔다.
- 화면 배치(Rev48~, 사용자 지적): 스크롤 상자에 위쪽 여백을 두면 표의 붙박이 머리 위로 줄이 비친다(`.bd.np` 는 위 여백 0). 화면 높이에 가두지 않은 화면은 본문(main)이 스크롤한다 — main 을 overflow hidden 으로 되돌리지 않는다. 화면을 고치면 `node tools/layout_check.js`(잘림 · 머리 틈 · 화면 오류, 문제 0)도 돌린다.
- 장치 대수 조정(Rev49~, 사용자 요구): 설비 제어 화면의 − · ＋ 는 자동 인식을 거드는 것이지 대수를 '입력'하는 것이 아니다 — 실장비에서는 장치가 응답해야 대수가 는다(`hmi/unitctl.py`). 뺀 장치는 두절 경보 없이 빈 자리로 돌아가야 하고(`unit_drop`, `hb_skip`), 연달아 눌러도 한 자리씩 잡혀야 한다(시험 있음). 개요 배치도에서 저장한 그림이 인식 대수보다 많다고 지우지 않는다 — '예비 자리'로 흐리게 둔다(사용자 지적: 추가하고 저장해도 반영이 안 됨). 대수 단추는 카드 제목 줄에 넣지 않는다(제목이 찌그러진다) — 그림 모서리에 둔다.
- 장치 구성 변화(Rev50~, 사용자 요구): 대수가 늘면 개요 배치도는 그림을 줄여 첫 장비 뒤로 겹쳐 세운다(흩어 놓지 않는다 — `layScale` · `layStack`). 장치 추가 · 철수는 FMEA(`ES-10`, 번호가 밀리지 않게 새 고장모드는 이 묶음이나 맨 끝 묶음에 넣는다 — 앞 묶음에 넣으면 FM 번호가 바뀌어 시나리오의 `ref` 가 틀어진다)와 시나리오('장치 구성 · …', 모의 신호 `UNIT.<장치>`)로 함께 다룬다. 기록에는 있는 장치의 값만 넣는다(`Fleet.clean`) — 뺀 장치의 직전 값이 운전 중인 것처럼 남으면 안 된다. 시험이 다른 장치의 통신 경보까지 넓게 확인하면 시험 장비가 느릴 때 흔들린다 — 확인 대상 장치의 경보만 본다.
- 차량 단위 대수(Rev51~, 사용자 지적): 대수는 차량 단위다. ① 복합전력 차량 = 디젤 + 계통 형성 ESS(G1): 디젤이 늘면 G1 용량 · 대수도 같이(`runtime.g1_n`). ④ 수소 차량 = 연료전지 + 수전해: 함께 늘고 준다(`unitctl.MATE`). 새 장치를 넣을 때 한 차량의 장치를 따로 늘리게 만들지 않는다. ⑤ EMS · ⑥ 배전 · 변압 · 주둔지 발전기 · 상전 수전점은 하나씩이다(대수 단추 없음). 태양광 차량 그림은 패널이 차량 '뒤'로 펼쳐진 형상이다(옆으로 펼친 그림으로 되돌리지 않는다).
- 복합전력 PCS(Rev52~, 사용자 정의): 기동형 복합전력공급체계는 발전기 + ESS 제품이고 PCS 가 둘을 연동한다(발전기 단독 · 발전기 + ESS 충전 · ESS 방전). EMS 의 통신 · 제어 · 감시는 PCS 를 거친다 — '복합전력 ESS 는 통신이 없고 EMS 는 감시만 한다'고 쓰지 않는다(예전 전제, 폐기). 대응표의 장치 이름 `DG` 가 그 PCS 다. 모드 선택은 `ifps_ems_rt/hybrid.py`. (Rev67 에서 바뀜 — 아래 '복합전력 ESS 를 같이 쓴다' 참고. 예전에는 이동형 ESS 가 맡지 못한 부족분만 방전했다.)
- 통신선(Rev52~, 사용자 지적): 통신선은 전력 케이블과 같은 경로로 그린다(구간분전함은 환형). EMS 에서 장치마다 따로 끄는 방사형으로 그리지 않는다. 환형 통신 장치는 설계 제안이며 상태 신호가 없어 통신 도달은 차단 구간으로 미루어 본다고 적는다.
- 복합전력 PCS 설정(Rev53~, 사용자 요구): 모드 값 · 이름 · 충전율 한계값 · 신호 주소는 관리자(엔지니어) 화면에서 고칠 수 있어야 한다(설정 편집의 '복합전력 PCS' 탭 → runtime.json 의 hybrid, pointmap.csv 의 DG.* 줄). 모드 값을 코드에 숫자로 박지 않는다 — `hybrid.settings(cfg)["code"]` · 화면은 `hyCfg()` 를 쓴다. 기본 시나리오 '복합전력 · …' 3건은 기본 모드 값(0~3)을 기대한다.
- 지령 지연의 원인(Rev53, 조사 결과): 전체 시험에서 지령 · 수집 시간 시험이 실패하던 것은 '시간 흔들림'이 아니라 구조 문제였다 — ① 자동 제어의 운전계획 계산(동적계획법)이 지령 처리 가닥에서 돌아 운용자 지령이 그 뒤에서 기다렸다 ② EMS 를 멈춘 뒤에도 예측 · 계획 계산이 10초쯤 더 돌며 다음 기동을 늦췄다. 그래서 운전계획은 뒤에서 계산하고(`PlanPolicy.background`, 계산 중에는 직전 계획 또는 규칙 운전), 멈추면 계산을 중단한다(`Engine.halted` · `Planner.cancel` · `attn.set_cancel` — 계산이 끝나면 조건을 지운다, 시작하지 않은 엔진에서는 중단하지 않는다). 지령 처리 가닥(`_exec_loop`)에 오래 걸리는 계산을 넣지 않는다. `sys.setswitchinterval` 을 줄이는 것은 계산 가닥끼리의 경합을 키워 역효과였다(넣지 않는다). 시험이 실패하면 '흔들림'으로 단정하지 말고 앞선 시험과 짝지어 재현해 본다(`tests.test_cover` + `tests.test_hmi` 로 재현됐다). `tools/static_report.py` 의 한 번 재시도는 남겨 두되, 재시도가 있었으면 보고서에 그대로 나온다 — '전부 통과'로만 말하지 않는다.
- 모듈 구성(Rev54, 사용자 요구 — 유지 · 보수가 쉽게): 제어화면 엔진은 `hmi/engine.py`(뼈대: 기동 · 정지, 수집 · 감시 주기)와 믹스인 `eng_alarms` · `eng_command` · `eng_auth` · `eng_view` · `eng_forecast` · `eng_tools`, 공용 `engdefs`(상수 · PIN 해시) · `alarmmgr` · `simdriver` 로 나뉜다. 새 메서드는 맞는 묶음에 넣고 engine.py 를 다시 키우지 않는다. 파일을 바꿔 쓰는 코드는 `ifps_ems_rt/fsio.py`(`write_text` · `write_json`)만 쓴다 — 임시 파일 뒤 교체를 모듈마다 되풀이하지 않는다.
- 실전 대비 원칙(Rev54, 감사 결과): ① 못 읽은 값으로 판단하지 않는다 — `rt.fresh(tag)` · `soc_blind()` · `grid_blind()`. - 가상 자료 가져오기 · 재생(Rev55, 사용자 요구 — 자료 형식은 받지 못해 일반 CSV 로 정함): `hmi/simreplay.py`(parse · Replay · action), 화면 `static/simreplay.js`, 요청은 `POST /api/sim` 의 `action: "replay"`. 재생 값은 SimDriver 의 hold 로 넣는다. 본문 한도(128KB) 때문에 한 번에 120KB · 5,000줄. 사용자가 자료 형식을 주면 `ALIAS` 와 `_time` 에 맞춰 넣는다.

- 개발 용역 의뢰 사양서(Rev68, 사용자 요구 — Word, 본문 11pt, 정부 문서처럼 쪽 구성이 깔끔하게): `docs/build_dev_spec.js`(공용 양식 `lib.js`). 수치는 측정 파일(static_results · test_results · forecast_benchmark · scenario_results)과 설정에서 읽는다 — 글에 숫자를 박지 않는다. 요구 기준은 '제안값'이라고 밝힌다. 장은 제목 문단의 '앞에서 쪽 나눔'으로 새 쪽에서 시작하고(쪽 나눔 문단을 따로 넣으면 빈 쪽이 생긴다), 코드 묶음 · 짧은 번호 목록은 한 쪽에 묶으며 코드 줄은 80자 이내로 쓴다. 기능을 넣거나 바꾸면 이 문서의 해당 요구사항(FN · UI · AL · …)과 '아직 구현하지 않은 것'(17.2)을 같이 고친다. 시험 항목 번호(T-xx)는 이 사양서의 번호다(별도 FAT 절차서 번호가 아님). - 사양서 제4판(사용자 요구 "화면 구성별 요구도, 하드웨어 운영에 따른 MIL 규정을 더 구체적으로"): 화면 12종마다 요구사항 표(OVW · SLD · RNG · FCS · TRD · DEV · LOD · SCN · ALM · RPT · COM · DBG)와 공통 창(DLG), 하드웨어 제안 사양 · 적용 규격 표 · 환경 시험(MIL-STD-810H 방법 번호) · 전자파(MIL-STD-461G 요구 이름) · 운용 조건을 넣었다. 시험 '수준'(온도 · 진동 · 전자파 한계)은 제안값 또는 '분석 단계 확정'으로 둔다 — 규격은 재단을 전제로 하고, 탑재 차량 · 쉘터가 정해지지 않았다. 내가 확인 없이 쓴 규격 번호가 틀릴 수 있으므로 문서에 '계약 시점의 최신 판 확인'을 적었다. 화면에 기능을 넣으면 그 화면의 표에 요구사항 줄을 더한다.

- 사양서 제8판(사용자 지시 "전자파는 MIL-STD-461 을 따라야 한다"): 전자파 적합의 기준 규격은 MIL-STD-461G 하나다 — 적용 요구 · 한계 · 시험 배치 · 측정 방법 · 제출 문서(통제 절차서 · 시험 절차서 · 시험 보고서)를 그 규격대로 쓴다. 내가 제6판에 넣었던 '국내 전자파 적합성 평가(인증 · 등록)를 따로 받는다'(EC-02)는 뺐다 — 민수 규격 성적서로 대신할 수 없다고 적는다.
- 사양서 제9판(사용자 요구 — 괄호 · 줄 넘어감, 줄간격 · 장평, 서술체 대신 간결한 기술 문체, 표 여백 통일, 예시 코드 문법 색): ① 이 문서의 글은 **개조식 기술 문체**다(요구사항 "~하여야 함 / ~할 것", 설명 "~함 / ~임", 한자어 기술 용어: 스냅샷 · 포인트 맵 · 시뮬레이터 · 버튼 · 심벌 · 절점 · 테마 · 임계값 · 스레드 · 패키지 …). 채팅에서 사용자에게 설명할 때의 '쉬운 말' 규칙과는 별개다 — 사양서에 새 글을 넣을 때 서술체(~한다, 보인다, 고친다)로 쓰지 않는다. 고유 용어(작전지 · 주둔지 · 저소음 · 환망 · 상시 개방점 …)는 그대로. ② 조판은 `lib.tune`(장평 95 % · 자간 −3 · 본문 양쪽 정렬 · 표 칸 여백 60/100 · 줄바꿈 규칙 `lib.tidy`)으로 이 문서에만 켠다. `tidy` 는 묶음 공백으로 가운뎃점 · 화살표를 앞말에 붙이고, 수와 단위 · 영문 뒤 조사 · 짧은 괄호(20자 이내)를 떼지 않는다. ③ 예시 코드는 `docs/codehl.js` 로 문법 색을 입히고 줄 번호 · 위아래 괘선을 넣는다 — 코드 한 줄은 화면 폭 90(한글 2칸) 이내로 쓴다(넘으면 줄이 접힌다). 쪽 구성 확인은 LibreOffice 기준이라 Word 와 한두 줄 다를 수 있다.
- **문서 글에 줄표로 구절을 잇지 않는다(사용자 지시, 사양서 제10판 — "앞으로 생성되는 모든 문서, Word · PPT · Excel 에 마찬가지")**: "신규 개발 — 운용 화면 …"처럼 줄표(— · – · 낱말 사이의 " - ")로 두 구절을 잇는 표현은 국어 문법에 맞지 않는 번역 투다. 마침표로 문장을 나누거나, 조사 · 쉼표 · 괄호로 풀어 쓴다(예: "신규 개발. 운용 화면 소프트웨어는 C# 으로 구현"). 표의 빈 칸에도 줄표 대신 "해당 없음"을 쓴다. 이 저장소에서 만드는 모든 문서(Word · PPT · Excel · HTML 안내)와 화면 문구에 적용하며, 기존 문서도 다시 만들 때 고친다. 범위(~)와 흐름(→)은 그대로 쓴다.
- **문서 글에서 낱말 사이에 가운뎃점을 쓰지 않는다(사용자 지시, 사양서 제11판 — 줄표 금지와 같이 모든 문서 Word · PPT · Excel 에 적용. 이 규칙 파일의 글은 예외)**: "구간분전함 · 배전체계", "배전 · 변압" 식으로 점(· ㆍ •)으로 낱말을 잇지 않는다. 둘이면 "및"(구간분전함 및 배전체계), 셋 이상이면 쉼표로 나열하고 마지막만 "및"(설계, 구현 및 시험)으로 쓴다. 사양서는 `lib.nodot` 이 만들 때 바꿔 주지만(원본 문자열에는 점이 남아 있다), 새 글은 처음부터 점 없이 쓰고, 다른 문서(보고자료 · 설명서 · FMEA · 워크북)는 다시 만들 때 같은 규칙으로 고친다. 날짜 · 판처럼 나열이 아닌 자리는 쉼표로 쓴다.

## 문서 작성 공통 규칙 (사용자 지시 — 앞으로 만드는 모든 문서 Word · PPT · Excel 에 적용, 이 규칙 파일의 글은 예외)

사양서 제7 ~ 11판에서 사용자가 하나씩 지적한 것을 모았다. 새 문서를 만들거나 기존 문서를 다시 만들 때 처음부터 지킨다.

1. **괄호와 줄 넘어감**: 괄호 안의 글이 줄 사이에서 갈리지 않게 한다. 괄호 안은 짧게(되도록 12자, 길어도 20자 이내) 쓰고, 길어지면 괄호를 풀어 문장으로 쓴다. 짧은 괄호는 통째로 다음 줄로 넘어가게 묶는다(Word 는 `lib.tidy` 의 묶음 공백).
2. **줄바꿈은 어절 단위, 문법에 맞게**: 낱말 중간에서 줄이 넘어가지 않게 하고, 수와 단위(20 kW), 범위(+10 ~ +35 ℃), 영문 뒤 조사(EMS 가), 화살표 앞뒤가 줄 끝 · 줄 첫머리에서 떨어지지 않게 한다. PPT · Excel 에서는 글상자 · 칸 폭에 맞춰 문장을 줄이거나 줄을 직접 나눈다.
3. **줄간격과 장평을 고르게**: 본문은 장평 95 %, 자간 약간 좁힘, 양쪽 정렬, 한 문서 안에서 같은 줄간격(Word 는 `lib.tune`). 쪽 · 슬라이드마다 글자 크기나 줄간격을 임의로 바꾸지 않는다.
4. **쪽 구성**: 제목은 뒤따르는 글과 같은 쪽에, 표 제목은 표와 같은 쪽에 둔다. 짧은 표는 한 쪽에 통째로, 긴 표는 머리줄을 되풀이하고 쪽 끝에 한두 줄만 남기지 않는다. 표의 한 줄(행)을 쪽 사이에서 자르지 않는다. 중간에 크게 빈 쪽을 만들지 않는다(장을 새 쪽에서 시작해 앞 쪽이 반쯤 비는 구성 금지, 부록만 새 쪽). 만든 뒤 PDF 로 바꿔 쪽마다 채움 비율과 빈 쪽을 확인한다.
5. **간결한 기술 문체**: 서술체(~한다, 보인다, 고친다)와 풀어 쓴 구어 낱말 대신 개조식(~함, ~임, ~할 것, ~하여야 함)과 기술 · 전문 용어로 짧게 쓴다. 이유를 길게 푸는 해설은 줄이되 조건(언제 · 무엇을 · 얼마 이내)과 수치는 남긴다. 채팅에서 사용자에게 설명할 때는 여전히 쉬운 말로 한다(문서 문체와 별개).
6. **표 여백 통일**: 한 문서의 모든 표는 칸 안 여백, 줄간격, 글자 크기, 머리줄 모양, 정렬(번호 칸 가운데 등)을 같은 값으로 한다. 같은 종류의 표는 열 폭 비율도 같게 한다.
7. **줄표 금지**: "개발 — 운용"처럼 줄표(— · – · 낱말 사이의 " - ")로 구절을 잇지 않는다. 문장을 나누거나 조사 · 쉼표 · 괄호로 푼다. 빈 칸은 "해당 없음".
8. **낱말 사이 가운뎃점 금지**: "배전 · 변압" 식으로 점으로 낱말을 잇지 않는다. 둘이면 "및", 셋 이상이면 쉼표로 나열하고 마지막만 "및".
9. **예시 코드**: 문법 색(키워드 · 자료형 · 함수 · 주석 · 문자열 · 숫자), 줄 번호, 위아래 괘선을 넣어 학술지의 코드 목록처럼 싣는다(`docs/codehl.js`). 한 줄이 접히지 않게 폭 90칸 이내로 쓴다.

사용자는 문서를 휴대전화의 Word 보기 프로그램으로도 본다. 확대해서 보므로 기호 하나, 줄 넘어감 하나가 눈에 띈다. 전달 전에 표지와 본문 몇 쪽을 크게 렌더링해 위 항목을 직접 본다.
- 수식의 곱셈도 점(·)이 아니라 " × " 로 쓴다(사용자 지시, 사양서 제12판).
- **표의 칸은 가운데 맞춤이 기본(사용자 지시, 사양서 제13판 — 모든 문서 Word · PPT · Excel)**: 가로 · 세로 모두 가운데. 긴 문장(한 줄 반을 넘는 글)이 있는 열만 열 전체를 왼쪽 맞춤(세로는 가운데)으로 둔다 — 한 열 안에서 맞춤을 섞지 않는다(`lib.tune` 의 `center`). 사용자가 긴 글도 가운데로 하라고 하면 그 예외를 없앤다.
- **문단 앞 검은 네모 표시 금지(사용자 지시, Rev69)**: Word 의 문단 설정 '다음 문단과 함께'(keepNext) · '문단의 줄을 함께'(keepLines) · '문단 앞에서 쪽 나눔'(pageBreakBefore)을 쓰면 보기 프로그램이 문단 앞에 검은 네모를 보인다(사용자는 휴대전화의 문서 보기 앱으로 본다). 세 설정을 쓰지 않는다. 대신 ① 표 설명은 표의 첫 줄(되풀이 머리줄)로 넣는다(`lib.CAP(…, true)` 뒤의 `TBL` 을 `lib.solid` 가 합친다) ② 제목 + 바로 뒤 문단, 예시 코드 + 설명은 테두리 없는 한 칸짜리 표(`lib.BOX`, 줄 나눔 금지)에 담는다 ③ 새 쪽은 제목 문단 안의 쪽 나눔 글자로 한다(상자 안의 쪽 나눔은 듣지 않으므로 그런 제목은 상자에 넣지 않는다) ④ 표가 잇달아 오면 한 표로 합쳐지므로 사이에 아주 낮은 빈 문단을 둔다. 만든 뒤 문서 XML 에 세 설정이 0개인지 확인한다.
- Rev69(사용자 지시 "Rev68 문서도 규율에 맞게 재정리"): 문서 작성 공통 규칙을 모든 작성기에 넣었다 — Word 는 `lib.js` 기본값(조판 · `tidy` · `nodot` · `nodash` · 가운데 맞춤 · 묶음 상자), PPT 4종은 만든 뒤 `tools/doc_rules.py pptx` 로 글을 고치고, 제안 발표 보완본은 새로 넣은 EMS 쪽만, 워크북은 보완하며 넣은 글만 고친다(사용자 원본의 글 · 수식은 그대로). `lib.js` 와 `doc_rules.py` 의 규칙은 같게 유지한다. **아직 안 한 것**: ① 사양서 말고 다른 문서의 문체(개조식 기술 문체로 다시 쓰기) ② 소프트웨어가 만드는 문서(운영 보고서 예시, 시퀀스 문서 PPT, FMEA · FAT 워크벤치 HTML, 교육용 가상 화면)와 화면 문구 · 화면 캡처 그림 속의 점 · 줄표 — 프로그램을 고쳐야 한다 ③ PPT 의 줄바꿈 · 표 맞춤.
- 정책 설명 자료(군 대상, 16:9 3장 — 사용자 요구. 처음에 A3 가로로 만들었다가 '16:9 로, 더 세심하고 알차게'라는 지적으로 다시 만들었다: 장마다 사진 카드 4 ~ 6개, 도형 아이콘, 화면 캡처 4종, 비교 상자, 지표 칸): `docs/ppt/build_policy_deck.js`(리비전 묶음에 넣지 않은 별도 자료, 출력은 `IFPS_EMS_정책설명자료.pptx`). 양식은 사용자가 준 참고 덱을 따랐다(왼쪽 단의 큰 번호 · 제목 · 병사 사진, 위 차림띠, 아래 남색 띠, 사진 카드, 비교 상자). 글은 모두 편집 가능한 글상자, 수치는 측정 파일에서 읽고 '시뮬레이터 검증값'이라고 적는다. 장비 그림은 `static/photos`, 화면은 캡처, 현장 사진(`docs/ppt/img/policy/`)은 생성 이미지라 '개념도'라고 적는다. 육군 로고는 공식 파일을 내려받지 못해(망 차단) 자리만 두었다 — 사용자가 공식 그림을 주면 넣는다. 참고 덱의 그림은 잘라 쓰지 않는다.
